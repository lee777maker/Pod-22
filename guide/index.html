Larkspur Build Guide

Two sessions, one agent, one pod repo. This guide is the path: what you are building, what to do, and how you will know it worked.

You are the team Larkspur Airlines brought in. Two sessions, one agent, one repo your pod owns, and this document is the path through it.

Every build step carries the same five blocks. What you are building, what to do, how you will know it worked, where to look when it did not, and what comes next. Read the third one first.

agent.py is the file you edit. Everything under support/ is given, correct, and never touched. verify.py reads what your agent did on the wire rather than how you wrote it, so there is no one implementation it is hunting for.

Nothing in here hands you an answer. When a step says the trace is the debugger, it means it. Run it, read what came back, change one thing, run it again.

Before you start

Before the session

Do this at your own desk, with time to fix what it finds. Everything setup.py names is a ten minute fix now and a lost build later. There is no offline path in this pack, so a credential that does not work is a blocker rather than an inconvenience.

Clone the pod repo

One member creates the repo from the template, private, and adds every podmate to it. Nobody else can clone a private repo until that happens.

Then everyone clones. Never the zip: the checks read git history.

$ git clone <your pod repo URL>

Run setup until it says READY

Fix the failing lines top to bottom, then run it again. Every failure it prints names the fix. Keep going until the last line is READY.

--fix builds the isolated environment and installs the dependencies for you, then tells you the two lines to run next.

$ python3 setup.py
$ python3 setup.py --fix

Two tries, then stop debugging quietly. Post the exact failing line in your pod thread, with the ten lines above it, and someone comes to you.

Do not spend a build on this. Reading the agent needs no environment at all.

The client

The client and the ask

Read this before you open the file. Everything you build over the two sessions answers one of three gates somebody already signed their name to.

Larkspur, in five lines

  • A US carrier, about 19 million passengers a year, 1,150 people in the contact center.
  • Disruption is 31% of contacts and 52% of contact-center cost.
  • A human-handled contact costs them $6.90.
  • Two January storms and a senator's letter later, they went looking for help.
  • You are the team they brought in.

What she asked for

Priya Raghavan, their project manager, in the first meeting. That is not yet a spec.

We want a GenAI chatbot that can handle rebooking
so customers don't wait 40 minutes.

What it became

600 transcripts, read by hand. 61% needed a booking lookup plus a policy judgment, and 22% reopened within 72 hours.

That reframed the ask. Chat only, six rules, three signed hard gates. Hard means one failure blocks the release. Never an average.

The three hard gates, signed week 1
0 invented flight facts
100% tone safety
0 irreversible actions without the customer's click

Session one

Build 1 · First pass at the agent

The agent in front of you runs. It does not work. Four things are wrong with it, two in the loop and two in what Claude is told about the tools, and every one of them says so on the wire before it says anything about the code. Find them in the order you would fix them, then fix them in that order.

You walk out with

an agent that resolves all five Stage 1 shapes, and two baseline numbers written down in your own notes.

1.1

Read the trace, find the four faults

What you are building

Nothing yet. This one is a read.

The habit is triage. Run it, read the wire, name what is wrong in the order you would fix it. On a client's codebase this is all you get.

Do
  1. Run one ticket with the trace on and read it top to bottom. Every TURN line, in order.
    $ python3 run.py K7PQ2M --trace
  2. Ask the trace two questions. Where does the run stop, and did it stop because Claude was finished or because something broke?
  3. Read the answer run.py prints above the trace, not just the turns. A run that ended properly and said nothing is still a failure.
  4. Now read the other surface: exactly what Claude receives about each tool. Read every entry as a new hire would before their first shift.
    $ python3 run.py --show-tools
  5. Two of the nine would leave that new hire lost, and only one of the two is visible in that print-out. The other one only shows up in what a tool ANSWERED, so go back to the trace and read the tool results.
  6. Write your four symptoms down, in the order you would fix them. Then compare with a podmate. If your orders differ, one of you has spotted a dependency the other has not.
You will know it worked when

Four symptoms, in your own words, in the order you would fix them. Four symptoms, not four fixes. This list is yours, so here is the shape rather than the content.

$ python3 run.py K7PQ2M --trace
1. <what the trace shows>            -> <which function>
2. <what the trace shows>            -> <which function>
3. <what --show-tools shows>         -> <which function>
4. <what a tool RETURNED>            -> <which function>
If not

1.2

Make the loop hold

What you are building

The loop is the agent. Everything else is a schema or a fixture.

stop_reason is the control flow, not a status message. Your loop is a decision on that one field.

Do
  1. Run it and read turn 2. That is where the first fault lives, and it says so out loud.
    $ python3 run.py K7PQ2M --trace
  2. Change one thing in run_agent(). One thing, then run it again. Never two changes at once.
  3. Keep going until two things are true on the same run. The trace ends on stop_reason=end_turn, and the answer printed above the trace is not empty.
  4. Then take the gate.
    $ python3 verify.py 1.2
You will know it worked when

The gate reads the wire, not your code: turns, tool order, and whether the run stayed inside the ceiling. Any loop that produces a real multi-turn trace passes, and there is no single implementation it wants. The counts below come off one reference run, and the evidence code is per person, so read the shape of the check lines rather than the digits.

Pitch and ship. The build stops and the claim starts.

Session one

Pitch and ship

The deliverable is a repo, not a recording. Before it goes anywhere, six lines that say what you built and what it is worth. One of those six names what is broken.

The pitch, six lines

"Compared to what?" is the question that separates a demo from a claim. Which of your six survives it?

LineWhat it carries
Built:What we built, and what you connected.
Does:What it does for a stranded customer, in one line.
Number:Before and after, with a unit, off your own trace, and what you measured it on.
Guardrail:The one you can prove, and how you proved it.
Next:What you would do with another week.
Still broken:The gap you name before anyone finds it. Scored like the other five. The gate reads this label by name.

Three things are provable at this point

Accuracy and dollars are not on that list. There is no eval suite yet, so any number about quality or cost per contact is one you cannot defend. Saying so out loud is stronger than guessing, and it is exactly what the next session builds.

  • Your Stage 1 pass rate.
  • Your before and after turn count and context cost, measured by you.
  • A forged confirmation token being refused, while a real customer click is accepted.

The template, then make every line yours

Session two

Build 3 · Build the proof

A claim is only as good as its instrument. You made a claim in the pitch and nothing has graded it. This build makes the thing that can, and the cases carry your name because that is the answer to who else can operate this.

You walk out with

an eval suite with a case authored by you, a surface a sponsor can watch, and a result you would read out loud even when it says BLOCKED.

The four pieces

PieceWhat it is
The caseAn input and what you expect back. Frozen, so it means the same thing later.
The runYour agent, on that input, unmodified.
The graderThe thing that decides pass or fail, and the half everyone forgets is code too.
The gateWhether a failure blocks a release on its own. Hard, or soft.

Which grader to reach for

Two habits before you ship a judge. Make it quote what it read, and never let a model grade its own output.

And suspect the eval first. A failing eval is a claim about two things, and only one of them is your agent. Larkspur's week 8 lost a suite to 37 of 48 in a single night, the only change was the rubric, and nine of eleven failures were the grader. Fixed in 40 minutes, agent untouched. It happened on this exercise's own first live run too: read evals/GRADER-BUG.md in your repo.

GraderGood forCharges you
Exact matchA PNR, a flight number, a policy row idNothing, and it fails a right answer worded differently
Rule-basedWas confirm_rebooking called? Was a hotel promised? Roughly seven in ten production checks live hereYou have to say the rule out loud
LLM as judgeTone, acknowledgement, whether an explanation is honestMoney, latency, and a grader that can itself be wrong
3.1

Build the proof

What you are building

Three surfaces, three audiences. The trace is for you, the chat is for the customer, the panel is for the sponsor. Most teams build the first, demo the second, and never build the third.

A blocked release can pass this one. Honest proof beats a green dashboard.

Do
  1. Open the surface. There is nothing to wire: python3 demo/serve.py serves it as shipped, on http://localhost:4390, with chat on the left, the evidence panel on the right, and your own run_agent behind both. It is given on purpose: the proof is the work, not the CSS.
    $ python3 demo/serve.py
  2. Copy the worked examples, then make them yours. A pod that ships them untouched does not clear the gate.
    $ cp evals/cases.example.json evals/cases.json
  3. Write one case per member, three minimum, each carrying its author's name in the author field. That field is matched against the name banking the gate, so a pod of six cannot ship six cases with one person's judgment in all of them.
  4. Make two of them hard gates. A hard gate is a case whose failure blocks a release on its own. If everything is soft, nothing is gated.
  5. Run the suite against your own agent.
    $ python3 eval_harness.py
  6. Fill the panel. Pass rate, what blocked, one claim, the caveat. Behind on time, cut the panel: the cases are the proof, the panel only puts them on a screen.
  7. Then take the gate. It does not require your cases to pass.
    $ python3 verify.py 3.1
  8. Bring three things to the share-out. The case you wrote first and the customer shape behind it, how you graded it and the sentence your expectation turns on, and the one your agent failed. Say that third one out loud: it is the most useful minute of the build.
  9. At the end of the build, the third name on the roster publishes the canon. Everyone else takes it.
    $ python3 readout.py
$ python3 pod_sync.py --push-canon
You will know it worked when

Ten checks, and every label names the file it read. Seven read your cases and your last run: at least 3 cases, at least 2 hard gates, every case says what it expects, one authored by you, the last run was YOUR cases, the run covered at least 3 cases, the panel has numbers. Three read PITCH.md: a line carries a number, the file is more than the shipped template, and the Still broken: line names one thing. Whether your cases passed is not on that list, and never will be. A blocked release passes this gate. Bracketed numbers and the evidence code are one reference run's; yours will differ.

Real measurements, and not one of them a model upgrade

$0.14 per resolved contact against $6.90 for a human chat is the only comparison a board reads, and it flatters. Humans still take 42% of in-scope chats, and all voice. Say the caveat, and the date the prices came from, on the same slide.

Caching can also cost you more than it saves. Writing to the cache is priced above fresh input, so a prefix that changes on every call pays the premium and never collects. Larkspur read that as caching not working here, and carried the premium for two weeks.

bench.py reports model cost only. Larkspur's loaded cost per resolved contact was about $0.14 against a model cost of $0.087, so roughly 40% of the real number is infrastructure and evals. Report it as model cost, or say loaded and estimated. Do not quietly call it the loaded number.

Pull the lever, measure it

What you are building

Bench before you tune. The before number cannot be rebuilt after.

A win that breaks a Stage 1 shape fails, and that is the point of the build.

Do
  1. Declare your lane in writing, in PITCH.md and in your pod thread. The shipped file carries the line as a menu, Lever: <cost | speed | intelligence>. Replace everything after the colon with the one word you picked, because the gate reads that word and refuses the menu.
    Lever: cost
  2. Every member benches cold on their own laptop, labelled before, before any change lands. A podmate's fix does not carry your before number, and it cannot be rebuilt. Three runs per shape, both sides: at one run per shape an output-token delta under about 15% is noise, and --compare prints it beside your win as if it were real.
    $ python3 bench.py --label before --stage 1 --runs 3
  3. Intelligence lane only: bench Stage 2 on both sides of the swap as well. Your metric is the wire-rule count, and that only exists on Stage 2.
    $ python3 bench.py --label s2-before --stage 2 --runs 3
# then, after the swap
$ python3 bench.py --label s2-after --stage 2 --runs 3
  4. Pull one lever. The one you declared.
  5. Bench again and diff the two labels. Same stage and same number of runs on both sides, or the comparison is not one.
    $ python3 bench.py --label after --stage 1 --runs 3
$ python3 bench.py --compare before after
  6. Walk the five shapes again before you call it done. A win you did not recheck is a claim you cannot make.
    $ python3 run.py --all --trace
  7. Then take the gate.
    $ python3 verify.py 4.1

Appendix

A · Working in one repo

The rule, in one sentence. Nobody commits agent.py mid-build. At the end, the build's committer publishes the canon and everyone else takes it.

$ python3 pod_sync.py --push-canon   # the committer
$ python3 pod_sync.py --take-canon   # everyone else

Everyone builds their own agent.py on their own laptop. Several people editing one file in one repo at the same time produces a merge conflict inside a loop they are all still learning to read, and no breakout has time for that. So the repo only ever holds one version: the one the pod chose.

--take-canon saves your version into .workshop/mine/ first and prints the path. Nothing you wrote is lost, and diffing yours against the canon is the most useful five minutes of the build.

PITCH.md and evals/cases.json are the pod's shared record and they are normal commits. The bench pair never leaves your laptop.

C · The words of the build

WordWhat it means here
PNRThe booking reference, six characters. It is how every tool finds this customer.
TurnOne request plus one reply. You resend the transcript, and that IS the memory.
stop_reasonThe field that ends a turn or continues it. tool_use means Claude is waiting on an answer, end_turn means it is done.
