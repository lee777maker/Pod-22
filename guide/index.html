You are the team Larkspur Airlines brought in. Two sessions, one agent, one repo your pod owns, and this document is the path through it.

Every build step carries the same five blocks. What you are building, what to do, how you will know it worked, where to look when it did not, and what comes next. Read the third one first.

agent.py is the file you edit. Everything under support/ is given, correct, and never touched. verify.py reads the wire, meaning the requests and replies that actually went out, rather than how you wrote the code. There is no one implementation it is hunting for.

Nothing in here hands you an answer. When a step says the trace is the debugger, it means it. Run it, read what came back, change one thing, run it again.

1.1

Read the trace, find the four faults

What you are building

Nothing yet. This one is a read.

The habit is triage. Run it, read the wire, name what is wrong in the order you would fix it. On a client's codebase this is all you get.

Do
  1. Start the client surface and send K7PQ2M one message in it. Read what comes back. That surface is given, it runs as shipped, and it is where every symptom in this build shows up first. Leave the tab open; every step from here ends by sending the same message again.
    $ python3 demo/serve.py
$ open http://localhost:4390
  2. Run one ticket with the trace on and read it top to bottom. Every TURN line, in order.
    $ python3 run.py K7PQ2M --trace
  3. Ask the trace two questions. Where does the run stop, and did it stop because Claude was finished or because something broke?
  4. If a turn came back as an error, read the error line above the trace to its last word. run.py prints it whole. It is a statement about the conversation that went out, and the sentence naming what the API would not accept is usually the second one.
  5. Read the answer run.py prints above the trace, not just the turns. A run that ended properly and said nothing is still a failure.
  6. Read what each tool ANSWERED. The ↩ line under a ⚙ line is the tool's own reply, shortened. -v prints the whole of it.
    $ python3 run.py K7PQ2M --trace -v
  7. Now read the other surface: exactly what Claude receives about each tool, descriptions and the fields inside each input schema. Read every entry as a new hire would before their first shift.
    $ python3 run.py --show-tools
  8. Two of the nine would leave that new hire lost. One is thin where it should be a sentence. The other is a field that tells Claude the wrong thing about what to send.
  9. Now write it down in two columns. SEEN is what these two surfaces showed you, and which function owns each one. PREDICTED is one line: what do you think is hiding behind the thing that stopped the run? Then compare both columns with a podmate. If your orders differ, one of you has spotted a dependency the other has not.
You will know it worked when

Symptoms, not fixes, and a prediction. Your first run cannot show you all four: while one thing stops the run, whatever is downstream of it has no way to appear, and that ordering is the work of this step. So the deliverable is what you saw plus what you expect, and step 1.2 is where you find out whether the prediction held. This list is yours, so here is the shape rather than the content.

1.2

Make the loop hold

What you are building

The loop is the agent. Everything else is a description Claude reads or a function it calls.

stop_reason is the one field that says whether Claude is done or waiting on a tool. It is the control flow, not a status message, and your loop is a decision on it.

Do
  1. Run it and read turn 2. That is where the first fault lives, and it says so out loud.
    $ python3 run.py K7PQ2M --trace
  2. Now open agent.py. About 200 lines, and the loop sits at the top under three empty slots that hold things you write later. Below a ruled line are the nine tool schemas. One command prints the six places you edit, with the build and the step each one belongs to, and that is the map of the file. Nothing new ever arrives in it, so every step from here changes something already on your screen.
    $ grep -n '✏️' agent.py
  3. Change one thing in run_agent(). One thing, then run it again. Never two changes at once.
  4. Keep going until two things are true on the same run. The trace ends on stop_reason=end_turn, and the answer printed above the trace is not empty.
  5. Then take the gate.
    $ python3 verify.py 1.2
  6. Back in the demo: send K7PQ2M the same message you sent before you changed anything. A full answer comes back in the chat now, where a card was. That is the same fix, seen from the client's side.
You will know it worked when

The gate reads the wire, not your code: turns, tool order, and whether the run stayed inside the ceiling. Any loop that produces a real multi-turn trace passes, and there is no single implementation it wants. Before you take it, go and check your prediction from 1.1. The whole path

Five commands carry the build, and the repo's README carries the same five. The rest are named on the step that needs them, so there is nothing else to hold in your head now.

In this repo, claude gives you /setup, /build, /check and /readout. /build builds the step with you and never hands you the answer, and saying build the agent in plain words does the same, and /check runs the gate and translates what it printed, which is the shortest way in if you would rather not lead with a terminal.

Two more appear at the close, and neither is on the clock: python3 readout.py --client writes the page you can send a client, and ACCOUNT.md is 3 lines you type by hand.

$ git clone <your pod repo URL>      # once
$ python3 setup.py                   # until it says READY
$ python3 run.py K7PQ2M --trace      # every build
$ python3 verify.py 1.2              # every gate
$ python3 pod_sync.py --take-canon   # at the end of a build

The rule, in one sentence. Nobody commits agent.py mid-build. At the end, the build's committer publishes the canon and everyone else takes it.

$ python3 pod_sync.py --push-canon   # the committer
$ python3 pod_sync.py --take-canon   # everyone else

Everyone builds their own agent.py on their own laptop. Several people editing one file in one repo at the same time produces a merge conflict inside a loop they are all still learning to read, and no build has time for that. So the repo only ever holds one version: the one the pod chose.

--take-canon saves your version into .workshop/mine/ first and prints the path. Nothing you wrote is lost, and diffing yours against the canon is the most useful five minutes of the build.

PITCH.md and evals/cases.json are the pod's shared record and they are normal commits. The bench pair never leaves your laptop.

Who publishes the canon

One person pushes the canon at the end of the build. Agree who before the clock runs out. Everyone else takes it.

Two canon pushes in one build is the merge conflict this whole protocol exists to prevent, so it has to be one hand and the pod has to have said whose before the clock is out.

Behind, or something broke

The pod repo is the checkpoint. This restores what the pod pushed.

$ python3 pod_sync.py --take-canon --force
